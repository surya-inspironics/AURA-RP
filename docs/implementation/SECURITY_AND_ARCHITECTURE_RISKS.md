# AURA Security and Architecture Risks

**Audit date:** 21 October 2026  
**Scope:** Static inspection of the current repository plus baseline test/build output. This is not a penetration test, threat-model sign-off, legal opinion, or compliance certification.

## Highest-severity risks

| ID | Severity | Finding and evidence | Impact / recommended control |
|---|---|---|---|
| SEC-01 | Critical | `backend/app/routers/deps.py:get_current_tenant_and_user` accepts absent/invalid credentials and falls back to the first user. It also resolves an `X-Tenant-ID` directly without checking that the resolved user is a member of that tenant. Most general routers depend on this helper. | Unauthenticated access and cross-tenant access are possible on routes using this dependency. Disable the fallback outside explicit isolated demo mode; enforce valid active identity and membership for every request; add per-route anonymous, invalid-token, nonmember-header, cross-tenant read/write tests. |
| SEC-02 | Critical | Gold-loan router has authentication at router level, but `/disbursals/execute` and `/vault/seal` accept maker/checker/custodian IDs from request payloads; the service only compares strings. Pure servicing/collections endpoints use arbitrary caller-supplied loan and balance values. | Bearer authentication is not operational authorization. Bind all actors to authenticated memberships and roles; scope financial records to tenant and branch; make calculations preview-only until a persistent verified loan exists. |
| SEC-03 | Critical | Gold inputs are accepted as manual/simulated estimates; the device adapter manufactures signed readings using a generated process secret and hardcoded test devices. The persisted valuation workflow labels inputs/results simulated, but standalone valuation accepts client-provided values. | HMAC over simulator input does not establish a trusted physical measurement. Keep simulated values out of underwriting/disbursement; define a real gateway, device keys, calibration and anti-replay controls before accepting device evidence. |
| SEC-04 | Critical | Eligibility results depend on caller-controlled LTV/limits and market-rate adapter fallback. Static fallback is not marked stale in ordinary fallback path; no approved policy/rate source is required for the standalone valuation. `EligibilityEngine` truncates paise/gram to paise/mg and incomplete input guards permit invalid weight/deduction combinations in direct API use. | Financial calculation can be based on unapproved or malformed inputs. Approve units, policy, price and rounding; add strict validation and independently tested boundary vectors; fail closed for stale/unapproved rates. Do not claim regulatory compliance based on code comments. |
| SEC-05 | High | Generic decision workflow only blocks creator self-approval; it does not require `READY_FOR_REVIEW` or a passing validation state. General auth fallback may report owner. Gold decision endpoint blocks all approvals while simulator gates remain. | Approval controls are incomplete and inconsistent. Define authoritative state/role/limit rules and enforce server-side before enabling any approval. |
| SEC-06 | High | Seed code creates a Northstar demo organization and several users with a fixed shared demo password; startup always runs seed-if-absent. Local/demo fallback authenticates requests as the first user. | Demo credentials and fallback identity are unsuitable for any reachable shared environment. Remove or isolate seeded identities from deployed environments; provision secure initial owner flow; require environment-specific configuration. |
| SEC-07 | High | Two authentication stacks exist: Better Auth API route/config/schema and FastAPI JWT. Visible sign-in/up use FastAPI token stored in localStorage. Build output warns Better Auth base URL is unset and reports default secret use. | Divergent identity stores, callback behavior, session invalidation and authorization can occur; localStorage tokens are exposed to script access if an XSS occurs. Choose one authoritative session boundary, configure secrets/origins and protect browser credentials; threat-model XSS/CSRF. |
| SEC-08 | High | Audit chain verifier checks only that each `prev_hash` equals the prior stored `current_hash`; it never recomputes `current_hash` from persisted fields. Events are not enforced append-only by DB permissions, and some operations have no audit event. | A changed event payload/hash may evade the current verifier; record deletion/reordering and missing events are not guaranteed to be detected. Canonicalize and recompute every digest, enforce append-only controls, cover all material actions, and test tampering/deletion/reordering/concurrency. |
| SEC-09 | High | `EvidenceService` validates file extension, not actual content type; route reads full file into memory before 50 MB check; downloads do not verify checksum. Files are local filesystem writes separate from DB commit. | Resource exhaustion, extension spoofing, undetected at-rest alteration, orphaned files, and production storage loss risk. Stream with hard limits, inspect content, malware scan, reconcile DB/file transaction, verify digest on retrieval, define retention and backup. |
| SEC-10 | High | `main.py` calls `Base.metadata.create_all()` and seeds demo data at startup; no migration files were found. | Production deploy may create but cannot safely evolve schema; seed may add demo records; no tested rollback/recovery. Use explicit versioned migrations and controlled seed process, with backup/restore verification. |
| SEC-11 | High | Disbursal idempotency and custody state live in memory; repayment has durable order idempotency but no webhook/ledger/reversal. Test-mode provider statuses are not actual borrower-money settlement. | Restart, duplicate, retry, timeout and ambiguous outcomes can cause inconsistent or falsely represented financial state. Persist provider attempts and state; implement status inquiries/reconciliation and ledger postings before live money movement. |
| SEC-12 | High | Fixed/demo values appear in analytics and billing; dashboard has fabricated trend distributions, evidence counts, reviewer names, average time and at-risk count; billing invents usage/invoices/renewal when real records are absent. | Operators may make decisions from false KPIs or bill customers incorrectly. Expose provenance and remove demonstration fallbacks from operational tenant views; calculate from persisted records only. |
| SEC-13 | High | Several integration statuses/modes are global process singletons, not tenant-specific or audited. `GoldRateAdapter` has no consistent production-mode gate and makes external requests with static fallback. | Administrator actions may affect all tenants in one process; mode label may not mean provider is active; rate fallback can be mistaken for a valid price. Store approved configuration and change history with environment/tenant scope; gate source and freshness. |
| SEC-14 | Medium/High | `system/health` returns raw DB exception text; request timing middleware creates correlation IDs but does not pass them into most service/audit events. | Internal details may be disclosed and production troubleshooting/audit correlation is incomplete. Return generic health state externally; log safe diagnostics with redaction; propagate correlation IDs. |
| SEC-15 | High | Billing uses a fixed Enterprise plan and static invoice/renewal data; team invite uses a fixed bootstrap password rather than a verified invite flow. | False commercial representation and insecure account provisioning. Require verified invitation activation and contract-backed billing/entitlements. |
| SEC-16 | High | `next.config.mjs` sets `typescript.ignoreBuildErrors: true`; standalone `tsc --noEmit` reports an error in `components/GoldLoanCalculator.tsx` for `limits_comparison_paise`. | A green production build is not type-safety evidence and can ship incompatible frontend/API shapes. Remove bypass only after baseline is corrected and gate CI on type-check. |

## Architecture/operations observations

- **Single deployed implementation:** the runnable product is the nested Next.js/FastAPI/SQLAlchemy app. Top-level `backend/app/modules`, `frontend/src`, `contracts`, migrations, and infrastructure directories contain no implementation source files in this checkout. Do not scaffold a second backend or change UI without an approved decision.
- **Architecture decision record:** `docs/adr/ADR-001-STACK-RECONCILIATION-MODULAR-FASTAPI.md` selects preserving Next.js + FastAPI. Earlier gold-loan reconciliation notes recommend a Java/Spring implementation and are in conflict; the ADR is newer/marked approved, but product owner should confirm the source spec version.
- **Database/persistence:** SQLite fallback is useful for local development, not tenant-grade production isolation. Foreign keys/query filters do not equal a proven row-level security boundary. No migrations, backup execution, restore runbook validation, or data retention proof found.
- **Money and policy:** core case/decision models use floating point while gold calculations use integer paise. Unit conventions, currency, interest day-count, LTV caps, rounding, NPA/provision values, auction behavior and repayment order need approval. Treat constants and comments as implementation choices, not approved regulatory policy.
- **Background processing:** no queue, scheduler, transactional outbox, durable retry, notification job, or event recovery implementation found.
- **Observability:** health endpoint and response headers exist; no metrics, trace export, alert policy, or PII-safe operational logging policy found.
- **Deployment:** `docker-compose.yml` includes development fallback credentials and local exposed services. Never use these defaults in a shared or production deployment. `backend/run.py` starts Uvicorn with reload enabled.

## Unresolved decisions requiring owners

1. Which version of the original Gold Loan master specification and requirement artifacts controls? They are referenced by old docs but absent from the repository/ZIP inventory.
2. What unit, rate source, rate effective-time/staleness, purity basis, eligible-weight formula, rounding and LTV policy is approved?
3. Which Indian bank-specific policies govern day count, repayment waterfall, DPD/NPA, provisions, margin calls, notices, auctions, surplus refunds and customer disclosures?
4. Which identity provider/session model is authoritative: Better Auth or backend JWT?
5. What tenant/branch hierarchy and role/authority matrix apply, including delegated underwriting limits and dual control?
6. Which providers/credentials/contracts are approved for KYC, CKYC, bureau, screening, assay devices, market rates, bank payout, e-sign, notifications, auction and object storage?
7. What are audit retention/immutability, PII retention/erasure, residency, encryption/key rotation and recovery objectives?
8. Which payment callback, status inquiry, ambiguous outcome and reversal procedures are contractually supported?
